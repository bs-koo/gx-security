# GX 보안 점검

명시 호출 이름은 Claude Code `/gx-security:gx-security`, Codex `$gx-security`다. 별도 `gx` 단축 명령을 만들거나 요구하지 않는다.

사용자가 전문 스킬 이름이나 setup 순서를 기억하지 않아도 이 진입점에서 진행한다. 이번에 수행할 작업과 대상을 한 문장으로 알리고 필요한 절차만 실행한다.

## 의도와 대상

- 사용자가 지정한 폴더, 없으면 현재 프로젝트를 대상으로 한다. 플러그인 설치 폴더를 검사 대상으로 가정하지 않는다.
- “보안 점검해줘”, “출시 전에 봐줘”는 기본 **정적 출시 점검**이다. 명확한 요청에 목적·setup 여부를 다시 묻지 않는다.
- “변경한 부분”은 변경 점검, 발견 ID·수정 내역이 명확한 “다시 확인”은 이전 이력 재검증이다.
- “보고서 설명”, “지난 결과 보여줘”는 저장된 검사·대화 기록을 읽는다. 이 요청만으로 질문·준비 검사·새 스캔·설치·설정·대화 기록을 시작하지 않는다. 결과의 시각·범위와 당시 판정을 유지한다.
- “이 후보를 더 검토해줘”, “질문하면서 확인해줘”, “이전 질문을 이어가자”는 확인한 기존 실행·발견에 대한 [질문 기반 심층 검토](references/discussion.md)다. 과거 결과의 범위를 밝히고 필요한 코드 조사·질문으로 이어가며 새 스캔을 묵시적으로 시작하지 않는다.
- 목적 없는 단독 호출, 실제로 여러 가능한 대상·재검증 항목이 있으면 짧게 묻는다. 점검 중 보안 의미를 바꾸는 업무 의도는 아래 심층 검토 절차로 확인한다. 호스트의 질문 도구 또는 대화를 사용하고 실제 답이 필요한 해당 작업만 기다린다. 이미 받은 답·승인을 반복 요청하지 않는다.

## 내부 준비와 실행

실제 검사를 요청받았으면 [실행 환경과 이력 연결](references/runtime.md)을 읽고 준비 상태·설치 경로·기존 상태 저장소를 확인한다. 사용자가 `gx-setup`을 따로 호출할 필요는 없다. 설정 파일이 없어도 공통 실행기의 기본 설정으로 진행하며 `init`이나 프로젝트 파일 생성을 선행 조건으로 삼지 않는다.

사용자가 SEF 포크임을 알려줬거나 프로젝트 문서에서 그 근거를 확인했다면 실제 `check`·`release`·`retest`에 `--expected-framework SEF`(Windows 실행기는 `-ExpectedFramework SEF`)를 전달한다. 프로젝트별 setup 없이 필수 공통 보안 경계가 빠진 경우도 확인한다. `doctor`나 일반 프로젝트에 일괄 적용하지 않는다. 코드 모양의 유사성만으로 기반이나 방어를 보증하지 않으며 보호 정책의 필수 계약은 그대로 유지한다.

준비된 실행 환경에서는 다음 내부 절차를 적용한다. 링크한 전문 절차의 공통 실행기 사용 시에도 위 런타임 안내가 우선하며 호스트 Python을 무조건 실행하지 않는다.

| 요청 | 내부 절차 |
|---|---|
| 일반·출시 전 보안 점검 | [출시 점검](../checking-release-security/SKILL.md), 기본 `static-release` |
| 변경한 부분 점검 | [변경 점검](../checking-code-changes/SKILL.md), 명시한 기준을 보존 |
| 이전 발견 수정 확인 | [재검증](../verifying-security-remediation/SKILL.md), 원래 상태·발견 ID·프로파일 연결 |
| 실행 환경 준비만 요청 | [준비 확인](../preparing-security-checks/SKILL.md), 검사로 자동 확대하지 않음 |
| 기존 결과 해석 | 기존 `result.json`, `report.html`, 검토 묶음을 읽고 남은 질문 설명 |
| 후보의 업무 의도·권한 범위 심층 검토 | [질문 기반 검토](references/discussion.md), 기존 실행·대화 이력 연결 |

실행 환경이 부족하면 실제로 확인한 준비 항목과 다음 행동을 알린다. 도구 설치·이미지 준비가 필요한 경우만 일회성 선택을 묻고 기존 승인은 이어 쓴다. 선택하지 않은 설치를 반복 시도하거나 준비 실패를 보안 검사 결과로 꾸미지 않는다.

## 질문과 추가 조사

출시·변경·재검증 결과에 중요한 미확정 후보가 있으면 [질문 기반 심층 검토](references/discussion.md)를 적용한다. 코드로 알 수 있는 사실부터 조사하고, 사용자만 알 수 있는 업무 의도·허용 역할·자료 범위·배포 전제만 질문한다. 답변에 따라 실제 호출 경로와 방어를 더 확인하고 새 모호함에 후속 질문을 연결한다. 사용자 설명·관측 근거·불일치·미확정을 구분하며, 답변은 반증·예외·출시 승인이 아니다. 준비만 요청하거나 보고서를 읽기만 하는 경우에는 이 절차를 시작하지 않는다.

## 결과 전달

실제 판정, 검사 범위, 우선 확인할 항목·반대 근거·미해결 질문, 실제 보고서의 절대 경로를 전달한다. 미완료면 사용자가 해결할 구체적인 다음 항목을 말한다. 실행기 출력의 컨테이너 경로는 확인한 host mount에 맞춰 안내한다.
질문 기반 검토를 수행했다면 별도 대화 보고서도 전달한다. 의도와 구현의 일치는 해당 주장에 대한 조사 결과이며 전체 보안 통과를 뜻하지 않는다. 원래 `result.json`과 gate는 유지한다.

SEF·MyBatis 문맥과 공통 방어를 설명할 때는 [SEF 문맥](../checking-release-security/references/sef-context.md)을 적용한다. 기반 일치·문맥 제안·HTTP 거부·미검출만으로 반증이나 출시 통과를 승인하지 않는다. 소스 수정, 동적 요청, 외부 전송·배포는 현재 요청과 기존 보호된 정책의 권한 안에서만 수행한다.
