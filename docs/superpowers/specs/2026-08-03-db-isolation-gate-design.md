# gx-audit DB 격리 게이트 설계 (Spec)

**작성일:** 2026-08-03
**상태:** 확정 (브레인스토밍 완료 → 구현)

## 배경

`scope_guard`는 대상 **URL 호스트**만 검증하고, 그 서버가 뒤에서 **어떤 DB에 연결됐는지는 모른다.** 그래서 "서버는 로컬이지만 DB는 **공유 개발 DB(실데이터)**"인 흔한 조합에서 동적 검사가:
- **실데이터 노출** — IDOR로 실제 회원 PII를 회수
- **DB 오염** — 테스트 계정·픽스처가 공유 개발 DB에 쌓임
- **실데이터 훼손** — 파일 업로드 등 파괴적 검사

방금 sef-2026 세션이 안전했던 건 **도커 격리 DB를 의식적으로 띄웠기 때문**이지 플러그인이 강제한 게 아니다. `localdocker` 같은 격리 구성이 없는 프로젝트가 더 많아, 이 사각지대는 실질 위험이다.

## 핵심 통찰 (구조 파악 부담)

- **격리 DB (AI가 계정 생성)**: 가입 API·DB 스키마·필수 필드까지 **소스 정독** 필요 → 프로젝트별 맞춤(방금 세션이 증명).
- **개발 DB (사용자가 계정 제공)**: 계정을 만들 필요가 없으니 **로그인 방법만** 알면 됨(`--login-profile` 또는 로그인 소스 정독). 구조 파악 부담이 훨씬 낮고 오염도 없다.

## 설계 — 1.5단계에 DB 격리 게이트 추가 (라이브니스 다음)

### ① 자동 힌트
서버 설정(`application.yml`/활성 프로필)의 datasource url을 읽어 추정(참고용, 확정 아님):
- `localhost`/`127.0.0.1`/도커 포트(5433 등) → 격리 추정
- 원격 IP·사내 호스트 → 개발 DB 추정

### ② 사용자 확인 (AskUserQuestion, 필수)
"이 서버의 DB가 **격리/더미**인가, **공유 개발 DB(실데이터)**인가?"
- 옵션: `격리/더미(도커·로컬 전용)` / `공유 개발 DB` / `모름`
- **`모름`·불확실 → 개발 DB로 간주(fail-safe)**

### ③ 분기
- **[격리/더미 DB]** → 오염 무관. AI가 소스 정독으로 **가입·스키마·픽스처·테스트 계정 자유 생성**. 전체 동적 검사.
- **[공유 개발 DB]** → ⚠️ **오염 방지 모드**:
  - AI는 **계정·픽스처를 생성하지 않는다.**
  - **(가) 권장: 로컬 격리 DB 전환 안내** — 로컬이면 도커로 격리 DB를 띄워 격리 경로로 전환.
  - **(나) 개발 DB 그대로: 기존 테스트 계정 요청** — 사용자가 이미 존재하는 계정을 `read -rs` env로 제공. AI는 가입 구조 불필요, 로그인만(`--login-profile`).
  - **파괴적/쓰기 차단** — 가입·픽스처 삽입·업로드(`--allow-destructive`) 금지, **비파괴 읽기 검사만**. IDOR 등 읽기도 실데이터 회수 주의를 리포트에 명시.

## 구현 위치 (문서 중심)

- **주 변경**: `skills/auditing-web-application-security/SKILL.md` 1.5단계에 "DB 격리 게이트" 항목 추가(새 3번), 뒤 항목 번호 이동(계정입력 4·사전경고 5·Burp 6).
- **`audit.py` 코드 변경 없음** — audit.py는 계정을 만들지 않고 로그인만 하므로(픽스처 삽입은 SKILL 밖 AI 재량), 게이트는 대화형(SKILL) 지시로 충분. 파괴적 업로드는 기존 `--allow-destructive` 게이트가 이미 존재.
- **테스트**: SKILL 본문에 게이트 키워드가 들어갔는지 확인하는 메타 테스트(선택).

## 안전 원칙

- fail-safe: DB 상태 불확실 시 개발 DB로 간주(보수적).
- 개발 DB에서는 쓰기·생성 전면 차단, 읽기만.
- 격리 DB 전환(도커)을 권장 경로로 안내.
