# 탐지 규칙의 평가 범위

이 규칙들은 검토할 위치를 찾는 정적 탐지기다. 탐지 결과만으로 실제 악용 가능성, 운영 환경의 노출 여부, 수정 완료를 확정하지 않는다.

## 초기 검토 우선순위

현재 88개 규칙에 `metadata.severity`를 지정했다: High 44개, Medium 39개, Low 5개. 이 값은 검토 순서를 정하는 기본값이며 CVSS 점수나 검증된 취약점 등급이 아니다. Semgrep의 `ERROR`·`WARNING`과도 별개다.

| 규칙 유형 | 기본 우선순위와 이유 | 검토할 조건 |
| --- | --- | --- |
| SQL 조합, 요청값 기반 경로·파일 처리, 위험한 HTML 삽입 | High: 입력이 위험한 실행·출력 지점에 연결되는 후보 | 외부 입력의 실제 유입, 허용 목록, 인코딩·매개변수화, 도달 가능한 호출 경로 |
| 객체·관리자 접근, 토큰 검증 생략, 비밀값 보관·유출 | High: 권한 또는 자격 증명 경계에 영향 가능 | 상위 인증·인가, 객체 소유자 검사, 테스트 전용 값, 운영 설정 |
| 인증 설정·세션, CSRF, CORS, 리다이렉트, 일반 SSRF 호출 | Medium: 정책·운영 환경·다른 방어 장치에 크게 의존 | 공개 기능의 의도, 쿠키 사용, 실제 출처와 목적지, 요청 경로·프록시 설정 |
| 명시적 요청값을 사용하는 SSRF, 하드코딩 JWT 비밀값 등 | High: 같은 유형 중 더 직접적인 위험 연결을 표현 | 데이터 흐름과 실제 노출 여부를 별도로 확인 |
| 단순 API 사용·파일 이름·콘텐츠 타입·정규화 검사, 로그·DTO 단서 | Medium: 위험한 구성일 수도 있지만 정상 구현도 매칭 | 후속 검증, 민감정보 종류, 출력 대상, 공통 처리 계층 |
| stateless 설정, multipart 폼, CSRF 폼 검토 단서, 일반 콘솔 출력, 목적지가 확정되지 않은 반환값 | Low: 단독으로 위험을 입증하지 못하는 폭넓은 단서 | 이 단서가 실제 취약한 경로에 참여하는지 확인 |

등급은 각 YAML 규칙에서 확인할 수 있다. 정규식·단일 구문 기반 규칙은 오탐과 미탐이 있을 수 있다. 모든 SAST 결과는 `candidate` 및 `review_required: true`로 생성된다. 등급을 추가하거나 규칙 메타데이터에 `review_required: false`를 넣어도 검토를 생략할 수 없다. Medium·Low 후보도 미검토 상태라면 출시 판정이 `INCOMPLETE`다.

## 재현 가능한 평가

```powershell
python scripts/evaluate-rule-quality.py --engine semgrep --output rule-quality-results.json
```

기본 평가 엔진은 Semgrep 1.172.0이다. 설치 경로를 `--engine`에 직접 지정할 수 있다. 다른 엔진 버전을 시험할 때는 `--expected-version`을 명시하고 결과를 별도로 보관한다.

평가기의 기본 정답표는 [cases.json](../tests/fixtures/rule-quality/cases.json)이다. 기존 합성 프로젝트의 취약·안전 예제와 CORS 호출 순서·수신 객체 변형, JDBC 직접 조합·매개변수화·helper 변형을 포함한다. **28개 사례로 12개 규칙의 양성·음성을 평가하고, 나머지 76개 규칙은 미평가로 표시한다.** 다른 규칙이 우연히 같은 파일에 매칭돼도 그 규칙의 정답 검증 실적으로 세지 않는다.

여기서 정답은 **해당 규칙의 후보 경고를 기대하는지**다. `expected_match: true`는 악용 가능한 취약점의 확정, `false`는 애플리케이션 안전성의 확정이 아니다. TP·FP·FN·TN도 이 자체 작성 기대값과 탐지 결과의 일치 여부다. 별도 모델이 28개 라벨과 소스를 검토했지만 사람의 보안 평가, 외부 독립 벤치마크, 실행 가능한 앱의 공격 검증을 수행한 것은 아니다. [사례별 라벨 검토](research/credibility-hardening-2026-11-10/label-review.md)에 판단과 전제를 남겼다.

결과 JSON에는 엔진 버전, 규칙·정답표 해시, 사례별 기대값과 관측값, TP·FP·FN·TN, 미검사 파일, 평가한 규칙과 미평가 규칙을 기록한다. 엔진 오류, 다른 버전, 누락된 검사 범위는 `execution_complete: false`이며 누락 파일을 안전한 음성으로 세지 않는다. 원본 코드·매칭 구문은 결과 JSON에 복사하지 않는다.

2026-11-10에 Semgrep 1.172.0으로 위 28개 사례를 실제 실행했다. TP 13·FP 1·FN 1·TN 13, 미검사 0·엔진 오류 0이었다. 이 후보 탐지 기대값에서만 precision과 recall이 각각 13/14(약 92.9%)이며, 실제 취약성 판정 성능이나 제품의 일반 정확도를 추정하는 수치가 아니다. CORS 후보 양성 2개와 음성 대조군 3개는 기대대로 동작했다.

종료 코드는 `0`이면 실행이 완료되고 새 회귀가 없다는 뜻, `1`이면 예상하지 못한 미탐·오탐, `2`이면 실행 미완료다. **코드 0도 모든 사례가 탐지됐거나 모든 규칙이 검증됐다는 뜻은 아니다.** 알려진 미탐·오탐은 `known_limitation`으로 남기되 FN·FP와 precision·recall에 그대로 반영한다.

## 확인된 한계

- `access-vuln`은 ID를 매개변수로 받은 뒤 상수만 반환한다. ID 패턴을 찾는 대조군이며 IDOR를 입증하지 않는다. `auth-safe`·`access-safe`·`upload-safe`·`ssrf-safe`·`pathtraversal-safe` 5개는 관련 기능 자체가 없는 단순 음성 대조군이다. 정상 방어가 있는 실제 기능을 구별하는 능력은 이 5개로 평가하지 못한다.
- CSRF는 인증 방식과 상태 변경 요청, SSRF는 URL의 외부 통제와 실제 서버 호출을 확인해야 한다. CORS의 wildcard+credentials는 충돌하거나 위험할 수 있는 설정 후보다. Spring의 [검증 API](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/web/cors/CorsConfiguration.html#validateAllowCredentials())는 이 조합의 검증 오류를 명시하므로, 소스 패턴만으로 브라우저가 자격증명을 포함한 응답을 읽을 수 있다고 단정하지 않는다. 서로 다른 변수 이름도 런타임 객체가 다르다는 증거는 아니다.
- `sqisoft-spring-jdbctemplate-string-concat`은 문자열 조합이 별도 helper로 이동하면 같은 위험이 남아 있어도 놓칠 수 있다. 이 사례는 양성 정답이며 미탐으로 계산한다. 새 검사에서 사라졌다는 이유로 기존 SAST 위험을 수정 완료로 처리하지 않는 별도 보호 장치와 함께 사용한다.
- `sqisoft-vue-v-html-unsanitized`는 `v-html` 자체를 찾는 정규식이므로 `DOMPurify.sanitize`로 감싼 기존 안전 예제도 매칭한다. 이 사례는 음성 정답이며 오탐으로 계산한다. 정규식 예외만으로 sanitizer의 실제 동작을 보장할 수 없어 검토 단계에서 확인한다.
- SQL 양성은 term/title이 외부에서 통제되고 사전에 제한되지 않았다는 조건이다. DOMPurify 음성은 정상 패키지·적절한 버전과 설정·정상 실행·정제 후 위험한 재가공 없음이 전제다. 이번 합성 구문 검사는 이러한 런타임 조건을 검증하지 않는다.
- CORS 규칙은 동일 객체의 wildcard origin과 credentials 설정에 대해 두 호출 순서를 검사한다. 다른 객체의 설정, 명시적 신뢰 출처, credentials 비활성화는 음성 대조군이다. 프레임워크 버전·배포 설정에 따른 실제 CORS 동작은 이 구문 검사로 확정하지 않는다.
- 이 정답표는 자체 작성한 합성 회귀 자료다. 독립 평가자가 판정한 실프로젝트 표본, 숨겨진 평가 집합, 프로젝트 전체의 정확도 측정은 아직 없다. 여기서 산출한 precision·recall을 제품의 일반 정확도나 보안 인증 수준으로 홍보하면 안 된다.

규칙을 추가하거나 수정할 때는 해당 규칙 ID에 양성·음성 사례를 추가하고, 변형으로 발생한 미탐도 남긴다. 실제 프로젝트에서 확인한 오탐·미탐은 민감정보를 제거한 최소 재현으로 축적한 뒤 정답과 근거를 독립 검토하는 것이 다음 단계다.

다음 정답표에는 기능을 제거한 음성 대신 **동일 기능에 실제 방어를 적용한 대조군**을 늘린다. 객체 접근의 소유권 검사, 허용된 업로드 경로, URL 허용 목록, 쿠키/헤더 인증의 CSRF 차이, CORS 실제 응답과 객체 alias, 고정 버전 DOMPurify의 브라우저 결과를 포함한다. 후보 탐지 기대값과 실제 취약성의 실행 정답은 별도 항목으로 기록한다.
